# Catalog Percolation — the READ half

The catalog's *write* half (harvest → dataset → validate) made assets valid in git.
It did **not** make them percolate: nothing ingested the datasets, glossary, or
blast-radius edges into anything queryable. "Backing store: DataHub" was a thesis,
not a wire. That is the classic `exit 0 ≠ effect` trap — a green validate gate with
no downstream effect.

This is the read half that closes it.

## Pipeline
```
datasets/*/*.jsonl + glossary + gbrg edges
   │  tools/build_catalog_index.py   (ingest → unified index)
   ▼
catalog-index/{assets,glossary,edges}.jsonl + index.json   (queryable)
   │  tools/emit_datahub.py          (→ DataHub MCPs + recipe)
   ▼
datahub/catalog-mcps.json + recipe.yml   (loads into a GMS: `datahub ingest -c datahub/recipe.yml`)
```

## Query it (proves content comes back out)
```
python3 tools/catalog_query.py stats
python3 tools/catalog_query.py define <term>
python3 tools/catalog_query.py who-uses <repo-or-asset>
python3 tools/catalog_query.py blast-radius <asset_id>
python3 tools/catalog_query.py search <text>
python3 tools/catalog_query.py dataset <name>
```

## The canary (fail-closed)
`make verify-percolation` (wired into `make validate`, so every CI run enforces it)
rebuilds the index and FAILS if any dataset is uncovered, the glossary or edges are
empty, or a canonical query returns nothing. A control that cannot fail is suspect;
this one turns the build red the moment the catalog reverts to write-only.

## DataHub
`datahub/recipe.yml` is a file-source recipe; loading requires a running DataHub GMS
(`DATAHUB_GMS_URL`). The MCPs carry Dataset entities per catalog dataset and a
GlossaryTerm per glossary entry (with its definition + related terms). Regenerated by
`make emit-datahub`.

## Known freshness gap
The index reflects the datasets as committed. Assets added by very recent merges
(e.g. a new declared invariant in a gate merged minutes ago) appear only after the
next harvest/contribution — which is exactly what the contribution loop closes.
